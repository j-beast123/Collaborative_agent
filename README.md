# SHERPA

SHERPA trains a clinical collaborator Agent with online GRPO in a multi-turn Doctor–Agent discussion of
multiple-choice medical questions. At each training state a Rubric Generator writes one **ephemeral, state-local
behavioral rubric** from the pre-action context. The Agent is rewarded for downstream success and for satisfying that
rubric. In parallel, the Rubric Generator's prompt is periodically evolved, and a candidate prompt is accepted only if
its rubrics rank the Agent's stored responses more consistently with their downstream outcomes.

## Overview

```
                 current policy π_θ, generator prompt P_t
                                │
        realise one pre-action state h  (Doctor message before Agent turn t)
                                │
          structured pre-action context (elicited before any reply)
            ├─ Doctor-side context
            └─ Agent-side state
                                │
          G Agent responses from the same policy prompt
                    │                          │
     K matched continuations per response      one ephemeral rubric r = Gen(P_t, h, context)
                    │                          │
                  R_O(g)                     R_A(g)  (rubric score of each stored response)
                    └──────────┬───────────────┘
                  R(g) = w_O·R_O(g) + w_A·R_A(g)
                               │
                      on-policy GRPO update  →  π_θ'

  stored states, responses, R_O, R_A ──(every N steps)──► prompt search on Q_cov ──► P_t → P_t+1
```

The rubric never enters the Agent's prompt and is discarded after its state is scored; there is no persistent rubric set.

## Model roles

| Role | Model |
|---|---|
| Doctor (simulated physician) | `google/gemma-3-12b-it` (OpenRouter) |
| Agent (trained policy) | `Qwen/Qwen3-8B` + LoRA |
| State reconstruction | `google/gemini-2.5-flash-lite` (OpenRouter) |
| Agent-side Q1/Q2 judgment | current Agent policy, greedy |
| Rubric Generator, prompt reflection/refinement | `openai/gpt-6.1-sol` (OpenRouter) |
| Rubric gates and scoring | `typesafe/jev-1.13` (OpenRouter decisions) |

## Core signals

- **R_A** — how well a response satisfies the state's rubric: the judge's expected score on the 0/1/2 scale, divided by 2.
- **R_O** — downstream success: the fraction of K continuations (same seeds for every response) ending in the correct final answer.
- **Q_cov** — rubric quality for a state: the covariance of R_A and R_O across its responses (0 for an invalid or flat rubric). Defined only on states where R_O varies.

```
Agent learning:                 R = w_O·R_O + w_A·R_A   →  GRPO
Rubric-Generator prompt search: Q_cov                   →  P_t → P_t+1
```

The policy ratio uses the rollout policy that sampled the group; the frozen base model is used only for the KL term.
Rubrics are subject to validity and leakage checks.

## Fixed vs Evolving

Both conditions share the same initial prompt `P0`, the same structured context and the same Agent training.

- **Fixed** — `P0` generates every rubric.
- **Evolving** — every N steps, candidate prompts are generated by reflection on recent evidence, scored on the same
  stored responses and outcomes, and the best candidate is accepted only if its paired Q_cov gain is supported on held-out
  evidence. An accepted prompt generates the rubrics of all later states.

An Outcome-only condition (`w_A = 0`, no rubric) and the untrained Base model complete the comparison.

## Installation

```bash
pip install -e ".[train,test]"
export OPENROUTER_API_KEY=...        # or put it in .env at the repository root
```

Training cases are a JSONL file of MedMCQA-style items (`case_id`, `question`, `options`, `correct_option`), configured
in `data.train`. Question text is not redistributed; evaluation-only splits are protected through
`data/splits/protected_eval_v1.json` (ids and question hashes only).

## Tests

```bash
python -m pytest -q tests
python -m pytest -q tests/test_integrated_v1.py -k "end_to_end or resume"   # mocked end-to-end run with interruption/resume
```

The tests use mocks and a tiny CPU LoRA model; no API access or GPU is needed.

## Running SHERPA

```bash
python scripts/online_rl/run_integrated.py --condition integrated_evolving            # prints blockers or the preflight
python scripts/online_rl/run_integrated.py --condition integrated_evolving --launch
```

Conditions: `outcome_only`, `integrated_fixed`, `integrated_evolving`. The launcher refuses to start while any setting
in `configs/online_rl/integrated_v1.json` is `TBD` or `CALIBRATION_REQUIRED`, and resumes automatically from the last
committed step.

## Evaluation

`src/rq_eval` provides the evaluation harnesses; model and judge calls are injected.

- **RQ1** — task accuracy for Base, Outcome-only, Integrated-Fixed and Integrated-Evolving, with case-cluster bootstrap CIs (`main_table.py`).
- **RQ2** — behavior appropriateness judged by an independent frozen judge, never a training rubric (`appropriateness.py`); downstream effectiveness from matched continuations of each system's reply on the same histories (`downstream.py`).
- **RQ3** — Integrated-Fixed vs Integrated-Evolving, with the accepted prompt lineage (`rq3_analysis.py`).

`runs.py` loads a trained run with verified provenance (adapter, checkpoint, prompt and config hashes).

## Reproducibility

Every run writes a manifest with the config, condition, state-schema and prompt hashes. Each step commits its
evidence, the adapter checkpoint and its hash atomically. Seeds derive from `sha256(run_seed | key | role | index)`; the
Doctor API is not seedable, so cached continuations are treated as recorded samples. Prompt versions are
content-addressed and never overwritten.
